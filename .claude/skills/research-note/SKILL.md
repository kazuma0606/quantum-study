# 研究ノートの書き方

## 読者と文体

- 読者はリポジトリの持ち主本人（社会人の学習者）。天下りにせず、**途中式を省略しない**。「明らかに」「同様に」で飛ばさない。
- 文体は「です・ます」。曖昧な言い方（「具体っぽいが中身がない」説明）を避け、具体的な行列・数値で示す。
- 行列の成分を話題にするときは $a_{12}$ のように**成分名を明記**する（「右上の」で済ませない）。ベクトルの $(x,y)^T$ を初めて使うときは、$T$ が「縦に直して読む」印であることを書く。
- 逆行列が使えない場面（固有値での $A-\lambda I$ など）では、その理由と代わりの解き方（成分で連立方程式を解く）を書く。
- 証明せずに引用する事実は「知られている」「〜で示されている」と明示し、報告にも書く。

## 説明の粒度：書く前に毎回確かめる5点

方針の全文は `docs/note_style.md`。概念が「導出済み」かどうかは `docs/concepts.md`（表にあれば「○○ノートで導出済み」とリンクで済ませる。表になければ、初めて出る概念として詳解し、**同じコミットで表に追加する**）。

1. **初めて出る記号・用語は、使う直前に、意味と型（ベクトルか行列か、大きさ）を1行で述べる。**
2. **等号1つごとに、使った規則を書く。**「同様に」「容易に」「明らか」「計算すると」で飛ばさない。
3. **抽象的な式の直後に、2×2 など小さい具体例を、数値で最後まで追えるように置く。**
4. **主張を先に述べ**（箱で囲んだ式）、証明の方針、番号つきの手順の順に書く。前提にする知識は1行で復習する。使う関係式は、導出してから「以降はこれを使う」と明記する。
5. **書いたあとで、初学者として鉛筆で1回追う。**

あわせて：**説明の順序は「前提条件（復習）→ 式の提示（別行）→ 説明」**で、「復習は下にあります」と先送りしない／宣言（空間・ベクトル・演算子・次元の表）を使う前に置く／読む順で後ろのものを前で使わない／式は別行に／「〜でない」「必ず」「常に」は端点（ε=0,1 など）で成り立つか確かめる／**頼まれた範囲だけ直し**、構成の大きな変更は先に方針を示す。

## 書いたあとの流れ（品質ゲート）

1. 機械的な検査：`uv run python tools/lint_notes.py <ノート>`、`tools/scan_bars.py`、`tools/linkcheck.py`、目次の確認、`tools/update_md_headers.py --check`。
2. ノート1本、または大きな改訂ごとに、サブエージェントで監査する（編集せず報告だけ。指摘を直してからコミットする）：
   - `granularity-reviewer`：初学者の目で、説明の粒度と論理の飛躍、初出の概念の詳解を見る。
   - `math-auditor`：式を再計算し、端点・次元・量化・参照を見る。
   - `note-reviewer`：形式（式番号、縦棒、リンク、日付、テスト名と件数）を見る。
3. 細かい直しのたびには走らせない（1回に数分かかる）。

## 構成

1. タイトル `# 主題 ―副題―`
   - タイトルのすぐ下に、**作成日・更新日と2〜3行の要約**の引用ブロックを置く（リポジトリの Markdown はすべてこの形）：
     ```markdown
     > **作成** 2026-10-08　**更新** 2026-10-09
     > 何についてのノートかの要約（1行目）
     > （2〜3行で）
     ```
     要約は自分で書く。日付は `tools/update_md_headers.py` が git の記録から入れる（新しいノートでは日付の行に今日の日付を仮に書いておけばよい）。
2. 導入：何を扱うかを Part ごとの箇条書きで。
3. **関連ファイル**の段落：図のスクリプト、関連ノート、ノートブック、Lean へのリンク。
4. **記号の約束**の段落（必要なら）。
5. `<a id="toc"></a>` と `## 目次` と `<!-- toc:start -->` `<!-- toc:end -->`（中身は空でよい）。
6. `# Part I：…`、節は `## 1. …`（Part ごとに 1 から）。付録は `# 付録A：…`、節は `## A-1. …`。最後に `# まとめ`（表やコードブロックの要約）。
7. 式番号は `\tag{II-3}` の形（Part 番号-通し番号）。挿入で番号がずれたら振り直し、図のスクリプトの docstring・コメントの式番号も合わせる。

## 作業の手順

1. **数式を先に検証する**：書く前に、主張する式を SymPy（非可換記号も使える）・NumPy で確かめる。具体例の数値も計算して本文に使う。
2. 図が要るなら `note-figures` Skill に従って、図のスクリプトを先に作る。
3. 本文を書く。長い追記は、**シェルのヒアドキュメントを使わず**、Write ツールで一時ファイルに書いてから Python スクリプト（これもファイル）で差し込む。シェルを通すと `\\`（行列の行区切り）が `\` に化ける。
4. 目次を生成し、検査する：
   ```bash
   uv run python 研究ノート/tools/build_toc.py 研究ノート/…/note.md
   uv run python 研究ノート/tools/build_toc.py --check 研究ノート/…/note.md
   ```
5. リンクを検査する：`uv run python tools/linkcheck.py .`（0 件であること）。ブラケット記法を使ったら `uv run python tools/scan_bars.py note.md` も。
6. 新しいノートは `README.md` のフォルダごとの表に1行追加する。新しいフォルダなら節（`### 0N_名前`）を作る。関連ノート・ノートブックの README から、相互にリンクを張る。
7. 表の中で縦棒 `|` を数式に使うときは `\vert` にする（列の区切りと衝突する）。
8. **コミットの前に、見出しの日付をそろえる**：`uv run python tools/update_md_headers.py`（作成日は最初のコミット、更新日は本文が最後に変わった日。見出しだけの変更は更新に数えない。コミットしていない本文の変更があれば今日）。`--check` で、見出しが無い・日付が古いファイルを確かめられる。要約の内容がノートの中身と合わなくなったら、手で直す。

## 報告とコミット

- 報告では、何を書いたか（Part ごとの表）、確認したこと、証明せずに引用した事実、まだコミットしていない変更を書く。
- コミット・プッシュは、ユーザーに頼まれたときだけ。ファイルは**パスを1つずつ指定して** `git add` する（フォルダごとの追加はしない。ユーザーが別のセッションで並行して編集しているため）。
- 内容ごとにコミットを分ける。メッセージの末尾に、会話で指示された Co-Authored-By の行を付ける。
- クリストッフェル記号のノート（`christoffel_riemann_intro.md`）は、ユーザーが手で確認中のため、指示がない限り編集しない。
